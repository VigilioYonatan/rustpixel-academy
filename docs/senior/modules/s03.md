# S03 · API pública inestable

**Tipo:** reto guiado Senior Rust · **ID:** S03-C01 · **Estado:** material práctico preparado; no prueba de ejecución.

## Contexto profesional

Una librería expone tipos de implementación y panics para errores recuperables.

## Objetivo del laboratorio

Diseñar traits, enums y Result con compatibilidad y documentación.

## Restricciones y trade-offs

- Mantener contrato observable sin filtrar tipos privados.
- Toda afirmación de corrección debe incluir evidencia o describirse como hipótesis.

## Artefacto para inspección

**src/lib.rs · errores públicos** (ejemplo didáctico; no salida real del compilador)

```rust
pub fn read_config(path: &str) -> String {
    std::fs::read_to_string(path).unwrap()
}
```

**Pregunta del reviewer:** Define Result, tipo de error y pruebas de compatibilidad del contrato público.

## Decisión de diseño

Una librería expone panic! al recibir entrada inválida; ¿cómo evolucionas la API?

- **Opción A:** Conservar panic y documentarlo como éxito
- **Opción B:** Cambiar toda la API sin versión ni compatibilidad
- **Opción C:** Devolver un Result tipado y probar la compatibilidad observable

## Evidencias y criterios de aceptación

- [ ] Tests de compatibilidad API y documentación de errores.
- [ ] La explicación diferencia hechos observados de hipótesis.

- [ ] Se documenta la compatibilidad y el riesgo de regresión.

## Secuencia del escenario

1. Reporte de panic inesperado
2. Diseño de error público
3. Test de compatibilidad con consumidores

## Pistas progresivas

1. Enumera qué hechos están observados y cuáles son suposiciones.
2. Identifica el contrato de éxito y el caso adversario mínimo.
3. Define una prueba que fallaría si el problema regresa.

- Ejecutar `cargo fmt --all -- --check` y `cargo check --all-targets` en el crate del ejercicio.
